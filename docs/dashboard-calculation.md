## 1. นิยามช่วงวันที่ของระบบนี้

Dashboard และรายงานสรุป PDF ใช้นิยามเดียวกัน:

- เลือกเรื่องจาก `tickets.timestamp` หรือ “วันที่รับแจ้ง”
- วันเริ่มต้นและวันสิ้นสุดเป็นวันตามเขตเวลา `Asia/Bangkok`
- Query ใช้ช่วงแบบครึ่งเปิด `[วันเริ่ม 00:00, วันถัดจากวันสิ้นสุด 00:00)`
- สถานะ หน่วยงาน และคะแนนเป็นค่าล่าสุด ณ เวลาที่เปิด Dashboard หรือดาวน์โหลดรายงาน ไม่ใช่ snapshot ย้อนหลัง ณ วันสิ้นสุด

ตัวอย่าง วันที่ 1–31 กรกฎาคม 2569 แปลงเป็น UTC:

```text
timestamp >= 2026-06-30T17:00:00.000Z
timestamp <  2026-07-31T17:00:00.000Z
```

## 2. สูตรสถานะที่พิสูจน์ได้

ให้ `N` เป็นจำนวนเรื่องทั้งหมดในช่วงวันที่ และ `count(state)` เป็นจำนวนเรื่องที่มีสถานะล่าสุดตรงกับชื่อนั้น

```text
percentage(state) = count(state) / N × 100
```

Dashboard แสดงทศนิยม 2 ตำแหน่งสำหรับเปอร์เซ็นต์รายสถานะ

```text
start = รอรับเรื่อง

in_progress = รับเรื่อง
            + กำลังดำเนินการ
            + ศึกษาปัญหา
            + จัดทำนโยบาย
            + ของบประมาณ
            + จัดซื้อจัดจ้าง
            + ขั้นตอนทางกฎหมาย

finish = เสร็จสิ้น
forward = ส่งต่อ(ใหม่)
irrelevant_raw = ไม่เกี่ยวข้อง
follow = ติดตามเรื่อง
irrelevant_aggregate = irrelevant_raw + follow
managed = total - start
```

Invariant จาก Response ของ Traffy:

```text
total = start + in_progress + finish + forward + irrelevant_aggregate
```

คำว่า `managed` ใน API หมายถึงเรื่องที่พ้นสถานะรอรับเรื่อง ไม่ได้หมายถึง “จัดการเอง”

## 4. Feedback คะแนนต่ำในเรื่องเสร็จสิ้น

CSV ไม่มี `confirmed_case` จึงสร้าง KPI “รับรองการแก้ไข” ซ้ำอย่างถูกต้องไม่ได้ อย่างไรก็ตาม Snapshot ที่ตรวจพบว่าจำนวนเรื่องเสร็จสิ้นที่ได้ 1–2 ดาวบังเอิญเท่ากับ 808:

```text
finished_low_rating = count(state = "เสร็จสิ้น" and star in (1, 2))
                    = 592 + 216
                    = 808
```

เลขที่ตรงกันไม่ทำให้สอง field มีความหมายเดียวกัน: 1–2 ดาวคือ feedback คะแนนต่ำ ส่วน `confirmed_case` เป็นข้อมูลการรับรองจากต้นทาง Dashboard และรายงานจึงต้องเรียกค่า 808 ที่คำนวณจาก CSV ว่า **เรื่องเสร็จสิ้นที่ได้ 1–2 ดาว** เท่านั้น และห้ามใช้คำว่า “รับรองการแก้ไข” จนกว่าจะมี confirmed flag โดยตรง

## 5. สูตรที่ยังสร้างซ้ำจาก CSV ไม่ได้

### 5.1 จัดการเอง (`*_by_this`)

CSV มีรายชื่อหน่วยงานตอบกลับ แต่ไม่มี actor/org ที่เป็นผู้เปลี่ยนสถานะเป็นเสร็จสิ้นหรือไม่เกี่ยวข้อง การใช้หน่วยงานตัวสุดท้ายหรือค้นคำว่า “เขตทวีวัฒนา” ให้ผลไม่ตรง 7,394 และ 506 จึงห้ามเดาและห้ามแสดงเป็นศูนย์

ข้อมูลที่ต้องเพิ่มอย่างน้อย:

- ผู้ดำเนินการหรือหน่วยงานที่เปลี่ยนสถานะ
- เวลาที่เปลี่ยนสถานะ
- organization ID ที่อ้างอิงได้แน่นอน

### 5.2 เวลาที่ใช้แก้ไข `4–98 วัน`

Endpoint `get-period-time-post` ส่งผลสำเร็จรูปว่า:

- ประเภทปัญหา: ทั้งหมด
- ฐานเวลา: เดือนที่เสร็จ
- metric: เวลาที่ใช้แก้ไข
- ผลลัพธ์: 4–98 วัน
- เดือนที่คำนวณ: กรกฎาคม 2569

Response ไม่มี raw completion timestamp, sample count หรือวิธี aggregate จึงยังพิสูจน์ไม่ได้ว่า 4–98 เป็น min–max, percentile หรือการตัด outlier แบบใด และห้ามใช้ `last_activity` แทนเวลาปิดเรื่อง

## 6. ความสัมพันธ์กับรายงานสรุป

Dashboard และรายงาน PDF ต้องใช้เงื่อนไขเดียวกัน:

1. กรองเรื่องด้วยวันที่รับแจ้งตามช่วงวันที่กรุงเทพฯ
2. ใช้สถานะล่าสุดของ cohort เดียวกัน
3. ใช้จำนวนเรื่องทั้งหมดใน cohort เป็น denominator ของเปอร์เซ็นต์สถานะ
4. แยก “สถานะปัจจุบันของเรื่องที่รับแจ้งในช่วง” ออกจาก “เหตุการณ์ที่เกิดในช่วง”
5. ระบุชัดว่ารายงานสดไม่ใช่ snapshot ย้อนหลัง ณ วันสิ้นสุด

หากต้องการรายงานแบบสถานะ ณ วันสิ้นสุดจริง ระบบต้องมี lifecycle event ที่เก็บเวลาเหตุการณ์จาก Traffy ไม่ใช่เวลาที่ระบบตรวจพบตอน import
